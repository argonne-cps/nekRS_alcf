Two GPU faults in nekRS next on Aurora, and their fixes

The rbc example in nekRS next crashes on Aurora's Intel PVC GPUs. Two separate bugs cause this: one in nekRS's Schwarz smoother setup, and one in OCCA's SYCL code generator. With both patches applied, rbc runs to completion.

Fix 1: Schwarz weights used before they exist

Symptom

Every rank aborts during setup, while the pressure multigrid preconditioner is being built. The last lines before the crash are the float (wordSize=4) gather-scatter autotuning for the finest pMG level.

================= ELLIPTIC SETUP FLUID PRESSURE =================
...
building MG preconditioner ...
============= BUILDING pMG7 ==================
autotuning gs for wordSize=4 nFields=1
...
Segmentation fault from GPU at 0x90000, ctx_id: 1 (CCS) type: 0 (NotPresent), level: 3 (PML4), access: 0 (Read), banned: 0, aborting.
Abort was called at 288 line in file:
.../intel-compute-runtime-25.18.33578.77/shared/source/os_interface/linux/drm_neo.cpp

The fault address differs by rank (0x90000, 0x86000, 0x78000, 0x74000, 0x68000). Each one equals that rank's Nelements × Np × sizeof(pfloat). For example, 288 elements × 8³ points × 4 bytes = 589,824 = 0x90000. That pattern points to a kernel reading a full-size pfloat field from a null base pointer.

Where it happens

Host backtrace from a core file (trimmed):

#9  occa::dpcpp::stream::finish            occa/.../dpcpp/stream.cpp:16
#10 oogs::start                            src/platform/ogs/oogs.cpp:921
#12 pMGLevel::smoothSchwarz                ellipticMultiGridSchwarz.cpp:1280
#13 setupSmootherSchwarz()::autoOverlap::timeOperator   ellipticMultiGridSchwarz.cpp:1051
#15 pMGLevel::setupSmootherSchwarz         ellipticMultiGridSchwarz.cpp:1174   (autoOverlap())
#16 pMGLevel::setupSmoother                ellipticMultiGridLevelSetup.cpp:144
#18 ellipticMultiGridSetup                 ellipticMultiGridSetup.cpp:241
#20 elliptic::_setup                       elliptic.cpp:774

The sync at line 1280 only reports the fault. The bad read happens in a kernel queued between the previous sync (line 1261) and this one: the ogsExt unpack or postFDMKernel.

Root cause

pMGLevel::setupSmootherSchwarz() calls autoOverlap(), which times smoothSchwarz() to decide whether gather-scatter overlap is faster. On the ASM path, smoothSchwarz() ends with:

postFDMKernel(Nelements, o_work1, o_work2, o_Su, o_wts);

o_wts is only reserved and filled in generateSchwarzWeights(). That function was called at the very end of setupSmootherSchwarz(), after autoOverlap(). So during the timing pass, postFDMKernel receives an uninitialized buffer and reads Nelements × Np values starting at address 0.

When it triggers

Only when all of the following hold. autoOverlap() does no work otherwise.

  • Smoother is ASM, which is the default for the pressure solver. RAS does not use o_wts.
  • More than one MPI rank, on a non-Serial backend. platform_t turns ENABLE GS COMM OVERLAP off for a single rank or Serial mode.
  • ENABLE GS COMM OVERLAP is on, which is the default.

That covers most multi-rank cases that use the default pressure preconditioner, not just rbc. Other backends were not tested.

The change

Generate the weights before autoOverlap(). generateSchwarzWeights() only needs ogs (elliptic->oogs) and ogsExt, and both are set up earlier in the same function. It does not use the extended mesh freed after autoOverlap().

Fix 2: atomics on @shared memory compiled as global atomics

Symptom

Setup completes, then every rank aborts before the first time step completes:

initialization took 75.6841 s
Segmentation fault from GPU at 0x0, ctx_id: 1 (CCS) type: 0 (NotPresent), level: 3 (PML4), access: 2 (Atomic), banned: 1, aborting.

The backtrace stops in nekrs::udfExecuteStep(time=0, tstep=0) (nekrs.cpp:390), so the faulting kernel is in the case's UDF. The only atomic there is the hist kernel in examples/rbc/hist.okl:

@shared float cnt_s[2048];
...
@atomic cnt_s[idx] += w[id];      // atomic on work-group local memory
...
@atomic o[id] += cnt_s[id];         // atomic on global memory

Root cause

The SYCL source that OCCA generated for this kernel uses a global address space for both atomics:

auto & cnt_s = *(sycl::ext::oneapi::group_local_memory_for_overwrite<float[2048]>(item_.get_group()));
...
sycl::atomic_ref<float, sycl::memory_order::relaxed, sycl::memory_scope::device,
                 sycl::access::address_space::global_space>(cnt_s[idx]) += w[id];

A global-space atomic_ref on local memory is undefined behavior in SYCL. On PVC, the local-memory offset is treated as a global address, so the first access faults near 0x0.

OCCA does mean to handle this case. dpcppAtomicNode::print() emits local_space when atomic_type.hasAttribute("shared"). But @shared is attached to the variable (variable_t), not to its type. dpcppParser::setSharedQualifiers() confirms this, since it tests var.hasAttribute("shared"). So the check on the type never matches, and every @atomic gets global_space.

Who is affected

  • Any OKL kernel compiled for the DPC++ backend that uses @atomic on a @shared array. In nekRS that means user or UDF kernels.
  • No nekRS core kernel uses this pattern. All six core .okl files that contain @atomic were checked.
  • CUDA and HIP are not affected, because their atomics do not take an address-space parameter.

The change

When building the atomic node, pass in whether the variable is @shared, and emit local_space when it is. The old check on the type is kept, so behavior can only change for atomics on shared variables.

Verification

Translating hist.okl with the patched build (occa translate --mode dpcpp) gives the correct address space for each atomic:

sycl::atomic_ref<float,...,sycl::access::address_space::local_space>(cnt_s[idx]) += w[id];
sycl::atomic_ref<float,...,sycl::access::address_space::global_space>(o[id]) += cnt_s[id];

The full rbc case (PBS job 8991170) then ran 2840 steps to t = 100 and exited with code 0.

The case's kernel cache (.cache/) was deleted before that run. OCCA may not detect a translator change and could reuse the old compiled kernel.

Applying the patches

From the root of a nekRS next checkout:

git apply 01-nekrs-schwarz-weights-before-autooverlap.patch
git apply 02-nekrs-occa-dpcpp-shared-atomic.patch      # same OCCA change, with 3rd_party/occa/ paths
cmake --build build --target install -j 32
rm -rf <case dir>/.cache                               # force kernels to be translated again

For OCCA upstream, 02-occa-upstream-dpcpp-shared-atomic.patch has the same change with paths relative to the OCCA repository root.

Related issue, not fixed

In examples/rbc/hist.okl, the loop that fills the histogram checks if (id < nBin), where it should check if (id < N). As written, each rank only counts its first 256 grid points, so the values in pdf_scalar00.dat are far too small. This does not cause a crash, and it was left unchanged.
